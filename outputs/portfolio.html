An ELT pipeline that refuses to publish bad numbers

Raw claim files land; staging standardizes and tags every defect; a quality gate decides whether marts refresh; Finance totals are reconciled every run.

Business question

Can Finance, Actuarial and client teams trust that every dashboard number ties to what was actually paid?

What I built

SQL staging & marts (Snowflake-compatible, CI-tested on DuckDB), 9 automated checks with BLOCKER/WARN severity, a GL reconciliation with batch-level drill-down, a Snowflake TASK + ALERT, and a GitHub Actions workflow.

Claims vs. Finance GL

A bug the tests caught. The first version netted reversals using only the valid lines of a claim. When a reversal line failed a check but its original passed, the service was double counted. An integration test (test_no_quarantined_lines_reach_marts) found 22 such claims; the fix quarantines the whole claim.
Reconciliation SQL sql/quality/02_reconcile_finance_gl.sql
-- =====================================================================================
-- qa.recon_claims_vs_gl
-- Reconciles claims-extract paid dollars to the Finance general ledger (paid basis),
-- by client and paid month. Material variances usually mean a missing or late file,
-- not a math problem, so the output points at the batch-level detail to chase.
-- Tolerance: |variance| <= 0.50% of GL OR <= $500.
-- =====================================================================================
CREATE OR REPLACE TABLE qa.recon_claims_vs_gl AS
WITH claims AS (
    SELECT client_id, paid_month, SUM(paid_amount) AS claims_paid,
           COUNT(DISTINCT source_batch_id) AS batches_received
    FROM staging.stg_claims_lab            -- all deduped lines: GL books everything paid
    GROUP BY client_id, paid_month
),
gl AS (
    SELECT client_id, CAST(paid_month AS DATE) AS paid_month, gl_paid_amount
    FROM raw.finance_gl_lab_paid
)
SELECT
    COALESCE(g.client_id, c.client_id)                       AS client_id,
    COALESCE(g.paid_month, c.paid_month)                     AS paid_month,
    ROUND(COALESCE(g.gl_paid_amount, 0), 2)                  AS gl_paid,
    ROUND(COALESCE(c.claims_paid, 0), 2)                     AS claims_paid,
    ROUND(COALESCE(c.claims_paid, 0) - COALESCE(g.gl_paid_amount, 0), 2) AS variance,
    ROUND((COALESCE(c.claims_paid, 0) - COALESCE(g.gl_paid_amount, 0))
          / NULLIF(g.gl_paid_amount, 0), 5)                  AS variance_pct,
    c.batches_received,
    CASE
        WHEN ABS(COALESCE(c.claims_paid, 0) - COALESCE(g.gl_paid_amount, 0)) <= 500 THEN 'RECONCILED'
        WHEN ABS(COALESCE(c.claims_paid, 0) - COALESCE(g.gl_paid_amount, 0))
             <= 0.005 * ABS(g.gl_paid_amount) THEN 'RECONCILED'
        ELSE 'INVESTIGATE'
    END                                                      AS recon_status
FROM gl g
FULL OUTER JOIN claims c
  ON c.client_id = g.client_id AND c.paid_month = g.paid_month;
Snowflake stored procedure with quality gate snowflake/02_sp_refresh_lab_marts.sql
CREATE OR REPLACE PROCEDURE LAB_ANALYTICS.QA.SP_REFRESH_LAB_MARTS()
RETURNS VARCHAR
LANGUAGE SQL
EXECUTE AS OWNER
AS
$$
DECLARE
    blockers     NUMBER DEFAULT 0;
    recon_issues NUMBER DEFAULT 0;
BEGIN
    -- 1. staging (same SQL as sql/staging/*.sql)
    EXECUTE IMMEDIATE FROM '@LAB_ANALYTICS.QA.DEPLOY_STAGE/sql/staging/01_stg_claims_lab.sql';
    EXECUTE IMMEDIATE FROM '@LAB_ANALYTICS.QA.DEPLOY_STAGE/sql/staging/02_stg_member_months.sql';
    EXECUTE IMMEDIATE FROM '@LAB_ANALYTICS.QA.DEPLOY_STAGE/sql/staging/03_stg_claims_net.sql';

    -- 2. quality checks + finance reconciliation
    EXECUTE IMMEDIATE FROM '@LAB_ANALYTICS.QA.DEPLOY_STAGE/sql/quality/01_dq_checks.sql';
    EXECUTE IMMEDIATE FROM '@LAB_ANALYTICS.QA.DEPLOY_STAGE/sql/quality/02_reconcile_finance_gl.sql';

    SELECT COUNT(*) INTO :blockers
      FROM LAB_ANALYTICS.QA.DQ_CHECK_RESULTS WHERE SEVERITY = 'BLOCKER' AND STATUS = 'FAIL';
    SELECT COUNT(*) INTO :recon_issues
      FROM LAB_ANALYTICS.QA.RECON_CLAIMS_VS_GL WHERE RECON_STATUS = 'INVESTIGATE';

    IF (blockers > 0) THEN
        INSERT INTO LAB_ANALYTICS.QA.PIPELINE_RUNS (STATUS, BLOCKERS, RECON_ISSUES, MESSAGE)
        VALUES ('FAILED_QUALITY_GATE', :blockers, :recon_issues, 'Marts not refreshed');
        RETURN 'FAILED: ' || blockers || ' blocking checks';
    END IF;

    -- 3. marts (only reached when the gate passes)
    EXECUTE IMMEDIATE FROM '@LAB_ANALYTICS.QA.DEPLOY_STAGE/sql/marts/01_policy_flags.sql';
    EXECUTE IMMEDIATE FROM '@LAB_ANALYTICS.QA.DEPLOY_STAGE/sql/marts/02_client_month_metrics.sql';
    EXECUTE IMMEDIATE FROM '@LAB_ANALYTICS.QA.DEPLOY_STAGE/sql/marts/03_lag_triangle.sql';

    INSERT INTO LAB_ANALYTICS.QA.PIPELINE_RUNS (STATUS, BLOCKERS, RECON_ISSUES, MESSAGE)
    VALUES ('SUCCESS', 0, :recon_issues,
            IFF(:recon_issues > 0, 'Published; reconciliation exceptions sent to Finance', 'Published'));
    RETURN 'SUCCESS (recon exceptions: ' || recon_issues || ')';
EXCEPTION
    WHEN OTHER THEN
        INSERT INTO LAB_ANALYTICS.QA.PIPELINE_RUNS (STATUS, MESSAGE) VALUES ('ERROR', :SQLERRM);
        RAISE;
END;
$$;
02

Policy-adherence engine: where the avoidable dollars are

Seven evidence-based lab policies written as SQL rules, run against every payable claim. Each claim gets at most one finding and an avoidable-cost estimate that is defensible line by line.

Business question

How much of a plan's lab spend is avoidable, and which policies should we lead with?

Approach

Window functions and self-joins for frequency limits (HbA1c), look-back windows (presumptive before definitive drug testing), indication lookups for genetic tests, and an in-network median benchmark for out-of-network price.

Result

Avoidable allowed $ by policy, all plans, Jan 2024 – Jun 2026

Out-of-network price and genetic testing without indication lead; frequency rules are many claims, few dollars
  • Avoidable cost is the full allowed amount for tests that should not have been done, but only the price gap where a cheaper test answers the same question (definitive drug panel 22+ classes vs. 1–7; full respiratory panel vs. a targeted SARS-CoV-2/flu/RSV panel).
  • The HbA1c rule is evaluated from Jan 2025 so every test has a full 12-month look-back; earlier tests would be under-counted and make the program look worse than it is.
  • Seven unit tests on hand-built claims pin each rule's edge cases (e.g. a presumptive screen 19 days before passes; 30+ days fails).
Policy rules (excerpt) sql/marts/01_policy_flags.sql
-- P02: rolling 12-month count of HbA1c tests at or before each test
a1c AS (
    SELECT a.claim_id,
           COUNT(*) AS a1c_tests_rolling_12m
    FROM c a
    JOIN c b
      ON b.member_id = a.member_id
     AND b.cpt_code = '83036'
     AND b.service_date BETWEEN a.service_date - INTERVAL '364 days' AND a.service_date
     AND (b.service_date < a.service_date OR b.claim_id <= a.claim_id)
    WHERE a.cpt_code = '83036'
    GROUP BY a.claim_id
),
-- P03: same member, same routine test, same day, more than one claim
same_day AS (
    SELECT claim_id,
           ROW_NUMBER() OVER (PARTITION BY member_id, cpt_code, service_date
                              ORDER BY first_paid_date, claim_id) AS same_day_seq
    FROM c WHERE test_category = 'Routine'
),
-- P04: did a presumptive screen (80307) occur within 30 days before / same day?
def_drug AS (
    SELECT d.claim_id,
           MAX(CASE WHEN p.claim_id IS NOT NULL THEN 1 ELSE 0 END) = 1 AS has_presumptive
    FROM c d
    LEFT JOIN c p
      ON p.member_id = d.member_id
     AND p.cpt_code = '80307'
     AND p.service_date BETWEEN d.service_date - INTERVAL '30 days' AND d.service_date

Program impact, client ROI and performance guarantees

Plans went live on different dates, which is what makes a credible counterfactual possible: plans not yet live stand in for what would have happened.

Business question

How much did each client save, did we meet the guaranteed return on fees, and is any refund owed?

Approach

Imputation difference-in-differences: fit plan and calendar-month effects on untreated months only, predict each live month's expected PMPM, and price the gap. Recent months are completed with chain-ladder factors first.

Result

    Counterfactual estimator src/analysis/program_impact.py
    def fit_untreated_fe(df: pd.DataFrame, y: str, treat_col: str = "treated", trends: bool = TRENDS) -> pd.DataFrame:
    """Weighted LS of log(y) on client + month dummies using untreated rows; predict all rows."""
    train = df[~df[treat_col]]
    clients = sorted(df["client_id"].unique())
    months = sorted(df["service_month"].unique())

    nc, nm = len(clients), len(months)

    def design(d):
        # client intercepts + client-specific linear trends + common calendar-month effects
        X = np.zeros((len(d), 2 * nc + nm - 2))
        ci = d["client_id"].map({c: i for i, c in enumerate(clients)}).to_numpy()
        mi = d["service_month"].map({m: i for i, m in enumerate(months)}).to_numpy()
        rows = np.arange(len(d))
        X[rows, ci] = 1
        t = (mi - (nm - 1) / 2) / 12.0
        trend_cols = nc + ci
        keep = (ci > 0) & trends   # first client's trend is absorbed by the month effects
        X[rows[keep], trend_cols[keep] - 1] = t[keep]
        mask = mi > 0
        X[rows[mask], 2 * nc - 1 + mi[mask] - 1] = 1
        return X

    w = np.sqrt(train["member_months"].to_numpy())
    beta, *_ = np.linalg.lstsq(design(train) * w[:, None], np.log(train[y].to_numpy()) * w, rcond=None)
    out = df.copy()
    out["expected"] = np.exp(design(df) @ beta)
    resid = np.log(train[y].to_numpy()) - design(train) @ beta
    out.attrs["resid_sd"] = float(np.sqrt(np.average(resid ** 2, weights=train["member_months"])))
    return out

    AI-enabled analytics with guardrails

    A semantic model in Snowflake Cortex Analyst format lets account managers ask questions in plain English and get governed SQL, using the same metric definitions as the dashboards.

    Why the guardrail matters

    The classic mistake in this data is summing member months across test-category rows, which makes PMPM about five times too low. The semantic model documents the rule, and CI runs every verified query against an independent pandas calculation, including a check that the wrong version would be caught.
